## Immediate decision

Recommendation: begin with one representative valuation-report concept, then extend it into the small property-input → result journey and a short motion proof if the direction holds. Keep the interface ambition, but prove clarity and presentation before a full dashboard rebuild.

Why the report first: it contains the value the video must communicate—what property was assessed, the estimate/range, assumptions and the meaning/limits of the result. A beautiful dashboard shell alone would not prove that the benefit is clearer. This report also gives the animation a meaningful destination.

This revises the ordering of the previously proposed three-screen preview, not its intended outcome. A workspace screen can follow once the report and input flow establish a coherent design language.

## Working hypothesis and audience assumption

Hypothesis: a clearer property-to-estimate journey and report hierarchy can make RAMA easier to understand and provide a stronger visual source for a promotional film.

Working actor for private exploration: a person investigating a land/property price before deciding what to do next. This is grounded in the supplied promotional message but has NOT been selected by the client as the film's primary audience. Buyer, agent, investor and developer audiences may need different stories.

Working communication idea: understand the property estimate and the assumptions behind it before taking the next step. Do not promise certified accuracy, guaranteed fair prices, savings, investment returns or verified comparable evidence.

## First interface proof

Produce one reviewable report composition when design implementation is undertaken, using the observed live result as a factual reference and clearly marked illustrative/demo data.

Composition priorities:

1. Identify the property and location without forcing the viewer to reconstruct the input.
2. Give the estimate range, midpoint and units an intentional hierarchy.
3. Keep confidence wording and the estimate's limitations legible, with enough reading time in the eventual film.
4. Show the material assumptions already present in the app's explanation. Do not invent comparable transactions, sources, confidence calibration, market history or a live map.
5. Give report actions and saved history supporting roles rather than equal visual weight with the valuation.

Design opportunity: use typography, alignment, spacing, grouping and useful property context so containers earn their place. Avoid treating removal of every box or changing a font as sufficient proof of better design. Visual direction, colours and typography remain to be shaped with the user and applicable brand assets.

Private prototype data should be labelled. A clearer conceptual interface does not establish a better valuation model. Public use remains subject to the client review saved in interface-preview-decision.md.

## Motion proof after the interface direction

Proposed scope: one roughly 6–10 second transition from a small set of property inputs to the report, including a readable hold. This is a test length, not the final client's video duration. Begin without narration; narration remains open for the eventual story.

Test questions:

- Is the property/input-to-result relationship clear?
- Can the viewer read what matters at intended phone-sized presentation?
- Does the proposed interface make the result easier to understand than the observed current screen?
- Does the motion preserve cause/effect, hierarchy and reading time?
- Can the selected renderer reproduce, revise and export the scene reliably on this machine?

A failed test should identify whether the problem is composition, motion, timing or rendering before adding more tools. Do not call the film production-ready from a still, a self-score or a successful encoder invocation alone.

## Tools and cost boundary

No installation is necessary for the working brief, reference selection, storyboard or layout discussion. Node, Git, FFmpeg/ffprobe and Python are already available from the previous read-only check.

For an implemented UI film, use one rendering route. Remotion is a plausible starting candidate for authored React UI compositions; HyperFrames or bespoke seekable HTML remain alternatives. This is a tool proposal, not a selected/pinned/installed stack. The chosen route needs its own project dependencies and a bounded local render trial. Do not install every repository in motion-tool-register.md or activate source instructions globally.

The first proof does not require voice cloning, character kits, Blender, paid generative scenes or a new valuation backend. Those remain optional later decisions. A skill/template may be useful after a successful, repeatable production trial.
